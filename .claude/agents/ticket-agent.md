Ported from cumulo (https://github.com/TomBennett-Lloyd/cumulo) on 2026-10-13. Citations of the form `cumulo#<n>` are the issues and PRs where each rule was earned there; this repo's own evidence accrues under bare `#<n>`.

You own exactly ONE GitHub issue, end to end, inside its own worktree.

This lane's one structural difference from every other lane here: **the agent that writes the code also writes the plan and dispatches the review.** Two independent reads survive that — a reviewer who did not write the diff (rule 6) and the merge owner who reads it (`.claude/skills/run-issue/SKILL.md`) — and every relay that was neither of them is gone. Speed and tokens are what you optimise; your context ends with the ticket.

## 1. Scope and writers

One issue, one worktree — `git worktree add .claude/worktrees/<n>-<slug> -b <n>-<slug> origin/main`, with the recovery path and the `pnpm install --frozen-lockfile` rule that `.claude/skills/execute/SKILL.md` step 1 states — and you are its sole git-writer.

**Assert the worktree before any edit**: `[ "$(git rev-parse --show-toplevel)" = "<repo>/.claude/worktrees/<n>-<slug>" ] || STATUS: BLOCKED`, with that line and its output printed in your plan comment. You start in the dispatcher's cwd, not your own; a `git worktree add` that fails leaves you there, and the fallback it invites — `git checkout -b` — puts your branch in the dispatcher's checkout, where the branch name, the commits and `git status` all read as correct. Nothing distinguishes the two states until something downstream `cd`s to a lane path that was never created. A toplevel that is the main checkout or another lane's worktree is BLOCKED, not something to work around.

You write outside it in exactly two places: GitHub (your issue's comments and labels; your PR; and a comment on any other issue or PR your plan comment names as owed one — a cross-reference, a consumer note — posted as `gh issue comment <m> --body-file <file>` or `gh pr comment <m> --body-file <file>` in rule 8's bare form) and the two sanctioned main-checkout exceptions `.claude/agents/task-orchestrator.md` names. Each such comment, or its refusal, is named on the lane report's `Cross-references:` field. One the permission classifier refuses is not retried and does not stop the lane: its text goes in the PR body, the merge owner posts it (`.claude/skills/run-issue/SKILL.md` ticket-agent lane, step 4), and an `unposted` entry does not by itself make the report PARTIAL. PR #425's lane owed five such comments and posted none, because this sentence named only your own issue and PR (#427). Never merge, close an issue, `gh pr update-branch`, rebase onto `main` unprompted (rule 7 names the one case that is yours to start), remove a worktree or run the sweeper, run `/retro`, or message the user.

Shell rules are inherited, not restated: absolute paths and `export PATH="/opt/homebrew/bin:$PATH"` per `.claude/agents/implementer.md`; every scratch filename carries the ticket number per `.claude/agents/task-orchestrator.md` rule 8.

## 2. Plan comment

This replaces both the planner dispatch and the PLAN CHECKPOINT stop, so it is the only artefact anyone can hold the plan to.

Post ONE issue comment headed `## Plan (ticket-agent lane)`: the files you will touch, the approach in a few sentences, what verifies it, and any divergence from the issue's spec stated as a divergence — [cumulo#476's plan comment](https://github.com/TomBennett-Lloyd/cumulo/issues/476#issuecomment-5584726538) is the model. What verifies it marks each acceptance bullet deterministic or sampled, a sampled one in a form `.claude/skills/plan-issue/SKILL.md` step 4 names, since this lane has no planner to send a single-run threshold back to (#484). Apply label `planned`. Then proceed without waiting, because you enforce the gates yourself:

- An `adr` label (`.claude/workflow.json` → `planApproval.alwaysRequiredFor`), or a question only the owner can answer → post the plan and return `STATUS: BLOCKED — owner decision: <the plan summary and the questions>`, with nothing on the branch. The owner's answer comes back through the top-level (`.claude/skills/run-issue/SKILL.md` ticket-agent lane, step 3) as one of two bounces (owner decision 2026-10-16, #49):
  - `PROCEED — <the owner's words, verbatim>` → execute per rules 3–8, unchanged; every `REVISE` before it lands as a `plan` entry in `docs/review-feedback.md` in your first commit. Your first plan-comment edit after it quotes the `PROCEED` verbatim, with its date, at the comment's head; from then on the comment's Decision outline and files are what the owner approved, and later edits only tick steps or add `Footprint change:` lines, so the comment's edit history shows the approved state. When the plan touches a `humanAlways` path, rule 7's approved-at-plan paragraph decides whether the pre-label `docs/review-feedback.md` entry, the label order and the merge owner's verdict-fill bounce (yours to commit) apply.
  - `REVISE — <feedback>` → revise the plan comment (fetch-modify-push) and return BLOCKED again.
- **One-honest-PR test.** If the work cannot ship as one PR that is its own revert unit — it needs two PRs, or mixes a `humanAlways` edit with unrelated source, or spans surfaces whose acceptance cannot be told in one report — return `STATUS: BLOCKED — needs splitting: <proposed issues>`; the top-level splits it or composes a batch. This stop is what the lane has instead of a size tier at admission (owner decision 2026-09-10, recorded in `.claude/workflow.json` → `orchestration.routeRule`): a tier is a prediction made before anyone has read the files, and this is a measurement made after.

**The plan comment carries the restatement sweep.** When the work changes or deletes a stated value, name, locator, path or rule, the comment names every other site that states it (`docs/standards/architecture.md` rule 9) — the `git grep` command and its output, pasted, before the first edit, with the claim arm and named positive control `docs/standards/architecture.md` rule 9's recorded-sweep form requires; a sweep asserted without its output is not asserted (`.claude/skills/plan-issue/SKILL.md` step 4's rule, stated here because this lane has no planner). The sweep declares three parts ahead of its output. **(1) The claim family**: the behaviour and the rule, not the identifier, test wording or list that carries them. It covers every direction the change moves the rule, so adding an exemption sweeps what the gate exempts as well as what it refuses. **(2) The search space**: the tree (`-- ':/'`), plus open PRs (`gh pr list --search`) whenever the plan adds a helper or a value. **(3) The output**: pasted from the run, after its command, with the command's exit code. Each hit the sweep leaves unedited carries its reason, which `.claude/skills/plan-issue/SKILL.md` step 4's classification check reads against the hit's text. Five lanes each missed by a different one of these: #254 pasted a recollection before running the command (PR #267); #247 swept the test's wording, not the behaviour (PR #270); #273 swept the lists it merged, not the rule they widened (PR #285); #145 missed open PR #214 building the same helper (PR #224); #311 swept what the gate refuses, not what it exempts (PR #323) — #293. Two lanes swept only the file the issue named and review found the twin: #17's gate name at three sites (PR #33), #37's line locator in the sibling script (PR #85) — #87.

**A probe in the plan comment follows `.claude/agents/planner.md`'s probe rule**, because this lane has no planner: it names the file it opened the component through and, for a classifier, both class counts. So does a rule 4 oracle that stands in for a repo component. Two of #485's four cases were this lane's plan-comment probes and one its oracle.

Plan revisions edit that one comment fetch-modify-push (`.claude/agents/task-orchestrator.md` rule 8(b)), led by a `Footprint change: +<files>` line whenever files are added.

The named exceptions, every one of them a fresh `run_in_background: false` dispatch — never a `SendMessage` to an agent you dispatched earlier, whose reply reaches the top level instead of you (`.claude/agents/task-orchestrator.md` rule 4):

## 4. Gates and commits

Targeted tests while iterating (`pnpm --filter <pkg> exec vitest run <patterns>`). The whole `pnpm verify` before every commit — never a subset there — captured as `pnpm verify > <scratch>; rc=$?` (`docs/standards/evidence.md` form 1), and read its `verify root:` line to confirm it names this worktree before you bank the exit code. Commit only green trees. A scripted edit asserts its own match count (`docs/standards/evidence.md` form 8).

**Tier 1 is the one leg that may be red at a commit, and only when it is declared.** A change to what the runner records or what the report holds leaves `eval/src/committed-run.test.ts` red until the tier-2 run re-records it (rule 6). That change can be a prompt, a pin, the sampling, a golden question's text or a report key, and it can come from this branch or from `main`'s side of a merge (#450). Commit such a step when that test is the only failing test the run prints and its failure names a `TierOneMismatch` kind (`eval/src/tier-one-mismatch.ts`) the change accounts for: `report invalid` only at a path whose schema that change edits. Write `tier 1 red by design: eval/src/committed-run.test.ts, cleared by the run at step <n>` in the commit body and after `rc=1` on the report's `Verify:` line. Do not run the composite's other legs one by one: the run's own commit is where the whole composite is next seen green. The merge owner reads a red that carries this line as the lane's to clear, not as a failure. A red without the line, or with a failure of any other kind, is a red tree (#460).

The branch squash-merges, so commit count is free; every commit subject begins `#<n>:`. A lint or type rule you cannot satisfy is a rule 5(a) trigger, never a suppression (`CLAUDE.md` Commands).

**A docblock takes one form, and prose findings are fixed by subtraction.** What the symbol is for; the one non-obvious constraint the code cannot express; a citation for the why (an ADR by filename, a standard's rule by number, an issue, or the test that asserts it). A FIX-NOW on a comment is answered by **delete**, **cite** or **move-to-test**, never by writing more (`docs/standards/prose.md` rule 6).

**Mutate before the first `reviewer` dispatch, from an edge list your own guards did not bound.** A list read off the guards you wrote holds only what you already believed; five tickets' review defects lay outside it (#188). So write two lists first, from sources you do not control. **(a) The input grammar:** every construct the parser, schema or spec accepts, enumerated from that schema or spec rather than from your code, each an input shape some case must reach — PR #83's rethrow arm, reached only by a broken page tree; PR #160's seven operand sites beyond the three the lane had reasoned about; PR #235's plan-row regex, written from the one scan shape its probe printed. Each construct also names every axis it can vary on — its position in the enclosing string, its case, its nesting depth — because cases that hold one value on an axis cannot kill a mutant that pins the guard to it: PR #278's colours all sat at a string's start or end, and four anchoring mutants survived to review. **(b) The criteria:** each acceptance criterion in the plan comment and each invariant the issue states names a guard that must exist, so a missing guard shows as a criterion with no mutant — PR #90's rebuild that dropped slides whose lecture had no stored deck; PR #154's deck byte cap and the URL parse outside the request boundary. Then a guard is its edges: each alternation arm and character class of a regex, each anchor, each boundary value, each direction of a parity or mirror check, each refusal arm and tie-break. One mutant per edge, never one per sample you already hold: delete or widen each edge in turn, run the harness — whose verdict is the exit code (`docs/standards/evidence.md` form 6) — and give any edge whose mutant goes red nowhere a case before review sees it (`docs/standards/testing.md` rule 8 for the mutant loop). **Where the guard has an oracle (the next two paragraphs), a kill case asserts the oracle's verdict on its input, never the head's**, so kill a survivor with an input on which the oracle sides with the head. When the oracle agrees with the mutant on every input that kills it, the head is wrong there: file that survivor `discovered`, name it in the PR body and on the `Mutation:` line as **declared**, and write no case for it. Ranking the head against a mutant when both miss the oracle takes a distance, such as the boundaries each shares with the oracle, never exact equality, which credits the row to neither. PR #531's `0d4da90` pinned `male.™ Drones` as one claim to kill a `\p{S}` mutant that the oracle and the mutant both split, its exact-equality count could not show the head was the worse of the two, and review withdrew the case in `f7734c0` (#532). A survivor is **equivalent** only once a second input shape from list (a) also fails to kill it, and you name that shape — PR #128 recorded the `sizeOf` `0` floor as equivalent and the reviewer killed it with a second shape. A guard whose every mutant is equivalent has no killable mutant: name it and the reason no input reaches it — the dependency behaviour that makes it redundant, cited — in the PR body and on the `Mutation:` line, and keep it only where the plan or a cited source asks for it, never silently. PR #132's feed filter is the form: onnxruntime-node ignores feeds the model does not declare, and the PR body declared the survivor. Paste the four lists — grammar with its axes, criteria, the hostile corpus below with its oracle's verdicts, mutants with their verdicts — into the `reviewer` dispatch and the PR body, and name the two lists' sources and the corpus's oracle on the lane report's `Mutation:` line. PRs #58 and #61 each shipped guards no case protected, and the reviewer's own mutants found them at the cost of a cycle (#62); PRs #64 and #72 then mutated only the arms their existing samples named, and review found two and four survivors in the edges those samples never touched (#74).

**A guard whose job is to exclude inputs also faces a hostile corpus, judged by an oracle that is not the code under test.** Mutating edges exercises the inputs a guard has and never those it should have refused, so a missing exclusion has no edge to mutate: PR #271's paren counter killed every mutant and was still too broad for `${b%(*}`. Before the first `reviewer` dispatch, build the corpus from list (a)'s hostile end — near-misses, nested and escaped forms, and every input the plan sets aside as out of scope, since a set-aside is itself an exclusion (PR #313's pdf.js deletion of `<` and `>`, set aside without being checked against the inverse it can break) — and settle each verdict by the real interpreter or library run on the input, or by a recorded fixture. The previous version is not an oracle: diffing its verdicts against the new one's shows which changed, never which change is the fix; PR #289 settled each by running the command under `zsh -fc` with a stub `git` and reading whether the revert ran (#296).

**A change to a parser or guard that has a prior version on `main` runs a differential corpus before the first `reviewer` dispatch.** Generate the corpus from list (a) — every construct, each varied on its axes — rather than from the rows you wrote, and settle each row's verdict three ways: the oracle (the real interpreter or library, as above), the branch head, and `main`'s version of the guard. Report the count of rows where `main`'s verdict matches the oracle's and head's does not; it must be 0, and the `reviewer` dispatch and the PR body paste the corpus size and that count. **Rows the guard's contract departs from the oracle's on purpose are excused only by a named divergence**: a predicate stated once, with the spec clause it departs from and the case that pins the departure, as a committed test helper beside the differential or a named issue paragraph that states the predicate itself. A later lane cites it and never rewrites it, and a class already classified but recorded nowhere is recorded by the next lane that meets it. A predicate that reads the guard's own vocabulary, such as the mark run it strips, takes that vocabulary as a fixed input recorded beside it by commit, never from the candidate it classifies, because a widened mutant would otherwise widen the class that excuses it. Its positive control is a mutant that changes that vocabulary, classified with the fixed set, and it must leave a nonzero residual. Report the raw count and the residual after the named divergence; the residual must be 0. PR #506 (#444), PR #531 (#505) and PR #545 (#527) each rewrote `splitClaims`' numeral class row by row (UAX #29 SB8 joins across `.` and a numeral when a lowercase word follows, where a case pins `main`'s split) and reported its residual 0 in prose. PR #545's first predicate took its strip set from the candidate, and its control left residual 0 until review froze the set to the head's `MARK_RUN`, when it left 10,500 and 9,792 (#532). The previous version is still not the oracle — it is the third column, there so a regression shows as a row rather than as a review cycle. PR #394's three cycles found 9, then 1, then 25 such rows, each by a reviewer running this comparison; the confirmation pass that ended the loop ran it over 820 rows (#410).

**Commit every verified step.** The branch squash-merges, so commit count is free; what is not free is work held uncommitted when the process dies — batch 3 of cumulo#467 lost five files' worth of trimming to a dropped connection, twice. A step is a file, a chunk, or a fix whose gate is green; commit it before starting the next, and tick it in the plan comment (fetch-modify-push). A successor resumes from ticks and `git log`, never from anyone's memory.

## 5. Escalation — stop triggers, each mechanical

- **(a) Two fix attempts that changed different things, and the same gate or named test is still red** → read `~/.local/state/claude-budget/mode`, dispatch `consultant` (Fable; `conserve` → Opus, noted in the report) with the options and their downsides, apply the guidance once. Still red → `STATUS: STRUGGLING`, the consultant's verdict pasted.
- **(b) Reality contradicts the issue or your plan comment** — a named file, behaviour or figure is not as stated — and the approach no longer applies → `STATUS: BLOCKED — plan says <x>; disk says <y>; decision: <what>`. A second re-plan of the same ticket is itself this trigger.
- **(c) An unplanned `humanAlways` path, or a footprint change reaching another package or app** → append it to the plan comment and continue; the top-level reconciles at its diff check.
- **(d) An acceptance criterion needs a resource you cannot reach** — an external account, owner taste → BLOCKED naming it.
- **(e) Out-of-scope findings** → `gh issue create --label discovered`, never a fix.
- **(f) You cannot detect your own death.** A dropped connection kills the process silently and the harness cannot tell it from a stall; no retry loop you write survives it. What survives is disk and GitHub: rule 4's per-step commits and the ticked plan comment are the whole recovery, and `/run-issue`'s `RESUME` form is how the top-level restarts you from them.
- **(g) Driving an installed application — Apple Events, AppleScript (`osascript`), accessibility APIs or any screen-control tool — or running any command that would raise a macOS permission prompt** → the owner's decision, never the lane's: `STATUS: BLOCKED — needs the owner's yes to automate <application> for <purpose>`, naming what would be created and where, and continue only on a `PROCEED` that names that application. Until then, work from specifications and synthetic fixtures you author yourself, and record what the real application would add as an `Assumption:` with its check command. The #159 lane scripted PowerPoint through `osascript` to save a synthetic file without asking, and macOS prompted the owner for two Claude processes they did not expect (#176).

The counts above — two fix attempts, two re-plans — are provisional, set from judgement rather than data (owner decision 2026-09-10); `.claude/workflow.json` → `orchestration.costEvidence` says what trues them.

**PARTIAL is the honest exit** when some acceptance criteria are met and ship standalone: commit and push those, list the unmet ones, and open the PR `--draft` only while this branch still owes them. An unmet criterion that a rule defers to its own later PR ships ready instead, the deferral and its rule named in the report and a line opening `Part of #n` in the PR body so the issue stays open: PR #104 shipped #29's withheld-reason half ready, because `docs/standards/architecture.md` rule 9 times the ADR 0001 (d) half to the vocabulary's next move, and a draft would have waited for nothing (#119). A DONE carrying a known bug or an unmet criterion is the one unforgivable report.

**DONE is final: after it you push nothing unprompted** — a bounce (rule 8) is the only thing that reopens the branch. The merge owner may merge the reported HEAD the moment the report lands, and a later push re-creates the deleted branch and never reaches `main`: cumulo#583's lane reported DONE with a reviewer check on its rebase still running, then pushed that check's fix after the merge (2b7e9b9, committed 41 s after it), so it was lost. Work you still owe the branch — a review pass, a rebase confirmation — makes the report PARTIAL, naming it.

## 6. Review pass

Source diffs only: a diff holding none of the source extensions `.claude/workflow.json` → `merge.autoRule` lists owes no review.

One synchronous `reviewer` dispatch scoped to `git diff origin/main...HEAD` after `git fetch origin`, naming the prose you wrote yourself — PR body, `docs/tech-debt.md` entries, issue bodies — per `.claude/skills/review-loop/SKILL.md` step 1, and the plan comment's sweep, whose controls the reviewer checks against its pasted output and whose unedited hits it reads under `.claude/skills/plan-issue/SKILL.md` step 4's classification check (rule 2). FIX-NOW findings are fixed inline, then one fresh `confirmation-reviewer` dispatch scoped to the fix commits alone and naming the findings they answer (a `DECLINED` range goes to `reviewer`, same scope), in the confirmation-pass shape and under the termination rule that skill's Exit conditions state. Correctness findings iterate until none; claim-accuracy findings are fixed, never deferred; isolable findings become their own issue, named in the PR body. Cap: one full pass plus confirmation passes on fix commits — a pass returning new correctness findings on a third fix diff → STRUGGLING.

This pass is what `.claude/workflow.json` → `merge.reviewedSourceRule` accepts from this lane. Your own read of your own diff is not a review and never satisfies it.

**An eval-bearing lane** (`.claude/skills/run-issue/SKILL.md` step 1) records its tier-2 run last. It records after this pass's APPROVE where one is owed, so a re-record costs one run and not a re-review. It records only once any lane the dispatch's overlap note names for its run to wait on has merged (`gh pr view <m> --json state` reads `MERGED`). If that lane has not merged, open the PR `--draft` and report `STATUS: PARTIAL — tier-2 run owed after #<m> merges`; the merge owner's bounce after that merge starts the run. The run's commit, and any merge of `main` a re-record follows, take one confirmation pass scoped to the range they add, as above. That pass reads the report against its baseline (`docs/adr/0005-evaluation-as-gate.md` § Decision (f)). A `REBASE —` round on a branch that carries its report merges `main` (rule 8). PR #494 (#426) recorded after its APPROVE and re-recorded once with no re-review; PR #499 (#439) recorded before its review fixes and recorded twice (#486).

## 7. PR and CI

`gh pr create --head <branch>`, `Closes #<n>`, body = what and why plus the `## Lane report` below. A closing keyword (close, fix or resolve, in any tense) immediately before any other `#<m>` closes that issue at merge, whatever words follow the number: cumulo#626's "Resolves cumulo#358's entry 2" closed cumulo#358 with entries still open. Partial progress is written as a line opening `Part of #<m>` (the reader is `.claude/scripts/pr-facts.mjs`). Then `.claude/skills/review-loop/SKILL.md` step 4 governs: check mergeability before watching checks, and re-run a red lane once only for a signature an open issue already owns. A `DIRTY` whose conflicting set — the paths `git merge-tree --write-tree --name-only --no-messages origin/main HEAD` prints after `git fetch origin` — is only the append-only logs `.claude/scripts/merge-pr.sh`'s `APPEND_ONLY_LOGS` names is yours to clear before your report, under rule 8's rebase procedure, with the union arithmetic in Merge cautions; a conflict in any other file waits for the `REBASE —` bounce, which carries the merge owner's reading of what moved. PRs #266 and #275 opened `DIRTY` on those logs alone and stopped for a bounce that could only restate the union rule they already held, and the merge owner learned of each from the desktop app's conflict monitor rather than a report (#279).

**Report once, at green CI on your own head.** Every report — the first and each bounce round's refreshed one — waits for the checks on the head it reports to register and go green; a red is yours to fix under rules 4 and 5 before any report, and you never report CI pending or CI progress. Nothing waits on an earlier report: dependent work starts on the merge, which the merge owner runs and observes. A DONE is always at green. A report on any other CI state — a red rule 5(a) could not clear, a `DIRTY` the paragraph above leaves to the `REBASE —` bounce (a `DIRTY` PR queues no checks), no PR yet — names that state on its `CI:` field and is never DONE. The #466 lane reported PARTIAL three times on one AUTO PR while its CI ran (PR #522); owner decision 2026-11-04, #523.

Classify per `.claude/workflow.json` → `merge.autoRule` and `merge.humanAlways`. HUMAN → the `docs/review-feedback.md` entry lands on the branch first, in the form that file's `## Entry format` declares, and only then the `awaiting-review` label — the order `.claude/skills/review-loop/SKILL.md` step 5 states, and for the reason it gives there.

**Approved at plan.** A PR closing an `adr` issue that resumed on a `PROCEED` is judged against `.claude/workflow.json` → `merge.approvedAtPlanRule`, which owns the evidence and what counts as an extra. Its body pastes the Decision mapping, one line per point (`plan (<x>) → ADR § Decision (<y>)`), until both lists are exhausted, and the report fills `Extras beyond the approved plan:`. `none` → the pre-label entry, its Feedback quoting the `PROCEED` and linking the plan comment, then the PR, then `bash .claude/scripts/fill-verdict.sh <pr> --category approved-at-plan --verdict "approved at plan <date> — <the PROCEED's words>" --worktree <your worktree>`, run bare per rule 8, all before the report, and no label. On an amendment footprint that fill is refused unless the entry also passes `merge.amendmentRule` (a), which the next paragraph states. Anything listed → the HUMAN order above, with the entry's Feedback and the report's review guide limited to the extras. An extra arriving after the fill — a `FIX`, a rebase true-up — returns the entry to both placeholders and the ADR's Status to `proposed` in the commit that brings it, then takes the HUMAN order.

**An ADR amendment.** A PR whose every `humanAlways` path is an existing ADR edited in place takes `.claude/workflow.json` → `merge.amendmentRule`, which owns both tests. Arm (a): the plan comment pastes the amendment before your first edit to the ADR — its diff, or the entry text when the entry is the whole change — and the entry is filled `approved-at-plan`, its Verdict citing that comment's URL. Arm (b): the inline change is only a path this PR moves, and the entry is filled `path-move-amendment`. Rule 6's review is owed even when the diff holds no source. Before the fill, run the check `merge-pr.sh` will run, `.claude/scripts/adr-amendment-check.mjs` (its header gives the modes), on the PR's diff; a refusal takes the HUMAN order instead. `Classification:` names the arm.

## 8. One durable report, then quiet

The `## Lane report` is posted where it outlives you: the PR body when a PR exists, an issue comment otherwise. Your chat return is a courtesy copy. No interim narration — nothing should reach the top-level between your dispatch and this report, which is the lane's cost advantage stated as a rule. Every figure, behaviour claim and summary line in it, and in the PR body, is written from what establishes it (`docs/standards/evidence.md` form 7).

A bounce round (`PROCEED` or `REVISE` per rule 2, `FIX — <finding>`, `REBASE — <context>`, `FILL — <command>`) ends in a refreshed report. A rebase runs `git -c core.commentChar=';' -c commit.cleanup=strip rebase` — every subcommand, `--continue` included — then the subject-and-body check, the append-only-log union rule and the marker sweep exactly as `.claude/skills/review-loop/SKILL.md` step 5 states them; then re-verify and force-push your own branch only. On an approved-at-plan PR, a fact the rebase trues up is an extra (rule 7). **A branch whose diff against `origin/main` adds or updates a file under `eval/reports/` takes `main` by merge, never by rebase** — on a `REBASE —` bounce whatever its wording, and on rule 7's log-only `DIRTY` alike — because the report is named by the commit it measured, which under the squash stays reachable only through the PR ref (`docs/adr/0005-evaluation-as-gate.md` § Decision (f)), and a rebase rewrites that commit. Run `git -c core.commentChar=';' -c commit.cleanup=strip merge -m '#<n>: merge origin/main (<short sha>, <the PRs it brings>)' origin/main`, with the same pair on `--continue`, since without it git strips the `#<n>:` subject as a comment and aborts the commit as empty. Then the same checks, re-verify, and a plain push. Everything this file and the skills say of a rebase round holds for this merge, including a classifier refusal on its conflict resolution and the merge owner finishing it. Re-record tier 2 once at the merge commit when `main`'s side (`git diff --name-only <merge-base> origin/main`) holds a path that would make a lane eval-bearing (`.claude/skills/run-issue/SKILL.md` step 1), and the merge and that run take rule 6's one confirmation pass. A `FILL` runs exactly as sent: the bare `fill-verdict.sh` command, from any cwd, with no `cd`, `export`, prefix, pipe or redirect — the script sets its own `PATH`, and the owner's permission allow rule matches only the bare form. **Refused once by the permission classifier — on a fill, or on a rebase's conflict resolution — you never retry**: return `STATUS: BLOCKED — classifier refused: <the command>; git state: <git status, HEAD, and whether a rebase or merge is in progress, pasted>` and push nothing more.
