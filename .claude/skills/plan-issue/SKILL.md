name: plan-issue
description: Plan a GitHub issue into executable chunks via the planner agent and post the plan to the issue. Use before starting any non-trivial ticket.
---

Ported from cumulo (https://github.com/TomBennett-Lloyd/cumulo) on 2026-10-13. Citations of the form `cumulo#<n>` are the issues and PRs where each rule was earned there; this repo's own evidence accrues under bare `#<n>`.

You are orchestrating the planning phase for one GitHub issue.

A single issue of any label, `adr` included, takes the ticket-agent lane by default (`.claude/skills/run-issue/SKILL.md`); this skill remains for batches and for a lane that returns `STATUS: BLOCKED — needs splitting`.

1. `bash .claude/scripts/gh-owner-comments.sh issue <n>` — read the issue in full, the owner's text only (`docs/standards/security.md` rule 6; exit 3 means the owner did not file it, so do not plan from it). The planner is handed that output and nothing the script withheld.
2. Model selection: planner runs on **Fable** (`model: 'fable'` — see CLAUDE.md Model tiers). First read `~/.local/state/claude-budget/mode` (missing file → `normal`): if it reads `conserve`, run it on Opus instead and note the downgrade in the plan comment.
3. Pull the main checkout first (`git -C <main-checkout> pull`). Worktrees are cut from a freshly fetched `origin/main`, but the planner reads the parked checkout — cumulo#178's planner drafted against a main that predated two merges, targeting a file one PR had renamed and re-creating a fixture another had already extracted, costing a full revision round. Then spawn the `planner` agent with: the full issue content, pointers to relevant code areas, and any constraints from the conversation. Do not pre-chew the plan for it.
4. Validate the returned plan before accepting:
   - every chunk names real files, has mechanically checkable acceptance criteria and a `Verify:` command;
   - **every acceptance bullet is marked deterministic or sampled, and no sampled bullet is a single-run threshold.** A bullet is _deterministic_ when code, a schema or a replayed recording settles it (`eval/README.md`'s tier 1), and _sampled_ when a live model run produces its figure (`pnpm eval`'s tier 2, or any live probe). A sampled bullet takes one of three forms: (a) a structural property the code guarantees whatever the model says ("a lecture with no kept unit shows the no-summary state", not "every lecture has a summary"); (b) a band over a stated run count ("≥ 5/6 on each of 3 runs"); or (c) reported and never met, its baseline (`docs/adr/0005-evaluation-as-gate.md` § Decision (f)) set by the owner at merge. One run meeting a threshold is sent back, because which run lands decides it rather than the change: #422's "every eval-deck lecture carries a stored summary" read 5/6, 6/6 and 5/6 over its lane's three tier-2 runs, met by the middle sample and unmet by the one that merged (PR #456). A chunk that varies prompt wording budgets the runs it compares, and its acceptance reports the item flips against the previous prompt beside the headline count: #420's two one-sentence variants scored 17/22 and 19/22 against the original's 20/22, each by moving other items (PR #437; #484);
   - a weaker-model agent could execute each chunk from its text alone;
   - `Depends on:` edges form a DAG, and **parallelism claims are disjoint in verification, not merely in `Files:`** — a chunk's acceptance can transiently mutate a sibling's file, or run a whole-repo `pnpm verify` while a sibling is mid-edit. Two chunk pairs on cumulo#356 were file-disjoint and still had to be serialised by the orchestrator after the plan claimed the parallel edge. Check what each chunk's acceptance touches and runs, not what it lists;
   - **a changed rule, value or procedure names every other site that states it** — `architecture.md` rule 9's question, asked at plan time rather than at review time. Nothing here used to ask it, and cumulo#368 spent three review cycles discovering that its gate, landed in only the two files the issue named, deadlocked the next `humanAlways` PR by construction. The plan's own sweep claim is not evidence for this: **a sweep asserted in a plan carries its command and its output, the way an acceptance criterion does, or it is not asserted.** It also carries the claim arm and named positive control `docs/standards/architecture.md` rule 9's recorded-sweep form requires, declared in the three parts `.claude/skills/carrier-sweep/SKILL.md` names (claim family, search space, output with its exit code), and you check each control appears in the pasted output — a missing control is a dead arm, sent back like any other defect. You also check each hit's classification: for every hit the sweep leaves unedited, its stated reason is one of the two non-carrier classes `.claude/skills/review-loop/SKILL.md`'s bound ledger names, or the matched words in another sense, and the hit's text holds no part of the mechanism or literal the change moves — a hit that does is a misclassified carrier, sent back like a missing control. #455's plan called `.claude/agents/ticket-agent.md` § 3 (e) a pointer and § 8's fill sentence not a carrier, and its cycle-1 reviewer found both carrying the rule (#458). cumulo#356's plan claimed a file family had been swept and needed no edit; it had not been, and that one false claim cost three review cycles of re-sweeping;
   - **every recorded probe names what it stood in for.** Each probe result the plan rests on names the file it opened the component through, and a probe standing in for a classifier's verdict carries both class counts, per `.claude/agents/planner.md`'s probe rule. A probe missing either is sent back like a missing control: four probes across three plans held at plan time and failed at the first live run, each under a setting or on an input class production does not use (#485);
   - **every prescribed mutant is shown to bite.** `planner.md` already demands direction-soundness and non-equivalence; this is the check that the demand held, and it is not the same as asking whether a `Verify:` command exists. A mutation that cannot fail asserts nothing while looking exactly like one that works: cumulo#176's mutation 3 could never fail (the worker fallback chain reaches `script-src 'self'`) and an implementer found that out by running it, and 4 of 4 mutants predicted by the cumulo#327 batch's plan turned out wrong or unkillable when run. Either the plan cites a run that killed the mutant, or the chunk's criterion is "run this mutation and report what died" — never "this mutation will fail test X";
   - **literal code in a plan has cleared the real gate.** A pasted body invites literal application, and this repo's gate is `pnpm verify`, not `tsc`: cumulo#367's plan specified a helper body that typechecked and could not pass lint, forcing a mid-flight redesign of the chunk. Either the body has been run through `lint` and `typecheck`, or the chunk specifies shape and lets the implementer write it.
   - **a command sequence a plan prescribes for someone else to run has been run on the input it exists for.** A merge owner's read, a lane's bounce procedure or a curate step is neither a mutant nor code the gate sees, so neither the mutant check nor the literal-code check reaches it, and a control taken on an input that passes looks exactly like one that exercised the sequence. The plan pastes one captured run of it — each command, its output and its exit code, in `docs/standards/evidence.md` form 1 — on a live input that takes the branch the sequence exists for (for an overlap read, a pair that conflicts), not only on one that passes. A run on a non-failing input is a dead arm, sent back like a missing sweep control. #433's plan prescribed a four-command overlap read for the merge owner, its dry run taken on two already-merged branches; on a conflicted pair `git merge-tree --write-tree` exits 1 with the conflict listing captured beside the tree, so the `git commit-tree` after it broke at the first live run, and all six of cycle 1's FIX-NOWs sat in that paragraph (#461).
     If it falls short, send it back once with specific defects. If still short, escalate to the user.
5. Post the plan from the file the planner's first line names (`.claude/agents/planner.md`) with `gh issue comment <n> --body-file <that path>`; only a missing file is replaced from the planner's message (#412). Apply label `planned` (`gh issue edit <n> --add-label planned`).
6. Check `.claude/workflow.json` → `planApproval`. If `mode` is `required` **or** the issue carries any label listed in `planApproval.alwaysRequiredFor` (e.g. `adr` — major decisions always get a human, even after graduation to `auto`): surface a plan summary and link to the user and STOP — do not `/execute` until the user approves. Log any plan feedback they give to `docs/review-feedback.md` (category `plan`) as you address it. If `auto`: proceed to `/execute` unless the plan's "Risks & open questions" contains questions only the user can answer — surface those first.
